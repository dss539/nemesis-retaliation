DESIGN OPTIONS · NOT IMPLEMENTED

Mobile UI — three competing architectures

All three keep the full Basic Action list always visible and scrollable — actions are what the player does, so nothing is hidden. Costs are the real rulebook values (p.13) and blocked actions state why. Geometry is corrected: corridors join only immediately adjacent hexes, and each gap is wide enough for a Door token plus Intruders standing in the corridor (the rulebook allows up to 6).

Problem 1 — Three-column desktop skeleton

The shipping layout is left panel / canvas / right panel. On a 390px phone two of the three columns must collapse, so player boards, action panel, card area and log all become off-screen tabs. Turn-critical facts end up behind navigation.

Problem 2 — Map and decision compete for the same space

Choosing a Move needs the destinations AND the board visible. The fix is a panel that shrinks during targeting, not one that disappears.

Problem 3 — Canvas map, DOM everything else

Room state lives in a 1500×1050 canvas, so tokens cannot be tapped as real controls, focused, or given accessible names. Every hex below is a real button.

Problem 4 — Action deck is a placeholder in the engine

createActionDeck() builds cards literally named move, shoot, useRoom — the same strings as Basic Actions. That is the real source of the card/action confusion. Only Sprint and Duck and Cover are confirmed from official sources; other faces are marked UNVERIFIED rather than invented.

OPTION 1

Command DeckMY PICK

Fixed bottom deck. Full scrollable Action list with real costs, then the card rail. Map never covered.

Trade-offs

  • Wins: actions are permanently primary and never behind navigation. Every row shows its true cost (0/1/2 cards) and blocked rows say why.
  • Wins: nothing overlaps the board, so the map never shifts under your thumb.
  • Costs: deck takes ~47% of height, giving the smallest map. Long action list needs internal scrolling.

Effort: moderate. CSS grid rewrite plus promoting the action panel out of the right column.

OPTION 2

Floating Action Panel

Map is full-bleed edge to edge. The Action panel floats over it as a rounded card, so the board extends behind it.

Trade-offs

  • Wins: largest usable map, because the board fills the whole stage instead of being squeezed above a fixed deck.
  • Wins: same always-visible action list as Option 1, so nothing is hidden.
  • Costs: the panel covers part of the board. You may need to pan to see hexes behind it, and the covered strip is unpredictable.
  • Costs: translucency over a busy map hurts text contrast in the worst case.

Effort: moderate. Same markup as Option 1, different positioning.

OPTION 3

Two-Surface Sheet

Map above, one draggable sheet below. The sheet auto-sizes to the current decision and lists choices as full-width rows with reasons.

Trade-offs

  • Wins: best at explaining why. Every action row can carry cost and a reason it is legal or blocked ("Door CLOSED, must open first") — exactly what the classification doc asks for.
  • Wins: map area is elastic. Sheet shrinks during targeting, grows for log and crew.
  • Costs: the sheet is still a panel over the map when expanded, and a resizing viewport can make the board jump under your thumb.
  • Costs: HAND / CREW / LOG behind tabs re-introduces the navigation problem, just less severely than today.

Effort: moderate-high. Needs a real sheet gesture layer and a per-state height policy.
